## Phase 5 - Payments, allocation and receipts (2026-09-30)

Added migrated payments, allocation and proof storage with gap-free per-year receipt numbering, the payment state/identity check constraints, a live-GCash-reference unique index, and database triggers that make a recorded payment, its allocations and its attachment append-only. A deferred constraint trigger proves both sides of every allocation: the standing allocations of an invoice always equal its paid column, and a payment's standing allocations never exceed the amount it received.

Implemented the allocation engine in the API. Money settles the subscriber's open invoices by due date, not by invoice number or issue order, continuing across invoices while money remains and holding the excess as credit. Credit is computed from the difference between posted payments and their standing allocations, so it keeps the identity of the receipt it came from and is spent oldest first against the invoices it predates. Allocation and credit spending take a transaction-scoped advisory lock per subscriber, so two collectors posting for one account serialise while different accounts do not block each other.

A GCash payment is stored as an inert claim: no receipt number, no balance change, no ledger entry. It requires a reference and a receipt image, the declared type is checked against the file's actual bytes, the stored name is generated with the exclusive-create flag, the resolved path may not leave the proof directory, the SHA-256 digest is recorded so a restored backup can be verified, and a failed transaction removes the file again. Only a second authorised user who did not record it may confirm it, which is where the receipt number is issued. Void applies to an entry that never posted and frees its reference; reverse applies to a posted payment, takes its own receipt number, posts a linked ledger debit, marks the original allocations reversed and reopens the invoices it had settled.

Added the named desktop payment operations and the Payments screen with a collect tab and a payment-history register. Desktop findings, each corrected before re-running: a successful payment left the confirmation and account panel unusable because the tab was remounted with a key to force a reload, so a revision value is now passed in and listed in the loading effect; re-picking the same receipt image did nothing because clearing the attachment emptied the React state but not the file control; a collector could not see why a posted receipt had been reversed, because the dialog showed the void reason but not the reversal reason; and the confirmation after a GCash confirmation omitted how many invoices were settled, so it now reports the count like the record message does. Diagnosing the last of these surfaced a Playwright behaviour worth recording: a failed test makes Playwright discard the worker and re-run beforeAll, so the next test silently received a brand-new empty database, which is why the GCash walkthrough first reported an empty register and receipt numbers restarting at 1001. It was confirmed with a two-test probe rather than guessed, and it matches the same failure recorded for the Phase 4 billing walkthroughs.
