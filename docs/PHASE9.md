# Phase 9 — Backup, hardening and deployment

## 1. Backup and restore (AT-12)

### What a backup is here

Two kinds, both recorded in `backup_history` so neither can be mistaken for the other:

| Kind | Carries | When it is the right answer |
|---|---|---|
| `FULL` | The database dump **and** the GCash payment proofs | What an operator means by "a backup of the office" |
| `DATABASE` | The database dump alone | A quick snapshot; recorded as incomplete, with `attachment_count = 0` |

A `DATABASE` backup is not a smaller `FULL`. It is a different promise, and the kind is stored so
the difference is visible in the history rather than inferred from a file listing.

### The shape of a backup file

```
backups/
  <uuid>.dump                     pg_dump custom-format archive
  <uuid>.dump.attachments/        copied payment proofs (FULL only)
```

The name is generated by the server (`<uuid>.dump`), never taken from a request. Both the API and
the desktop would otherwise be joining caller-influenced text to a folder.

### Why `backup_history` row is written before the dump

The row is inserted first, as `FAILED`, with the reason `Backup in progress.`

A backup that dies partway is a fact the operator needs to see. A history that lists only
successes hides a broken schedule until the day somebody needs a restore, which is the worst moment
to discover it. On success the row is updated to `COMPLETED` with the real size, digest, counts and
verification time; on failure the tool's own words are stored in `failure_reason` (capped at 400
characters by a check constraint) and the caller is told only that the backup failed and has been
recorded.

### Why a backup is not reported complete until it has been read back

The order in `BackupService.create` is deliberate:

1. insert the `FAILED` row, so a crash still leaves a record;
2. open a repeatable-read transaction and export a snapshot;
3. `pg_dump --snapshot=…` from that snapshot;
4. copy the proofs, checking each against the digest recorded when it was uploaded;
5. `pg_restore --list` the finished archive;
6. only then update the row to `COMPLETED` and audit `backup.create`.

Step 5 is the point. A dump that cannot be listed is not a backup, whatever its size on disk, and a
file that has never been read back is a claim rather than evidence.

### The snapshot, and why the counts are not read separately

The row counts a backup records are what a later restore is judged against, so they have to describe
the same data the archive contains.

Reading them in a transaction of their own would not do that. A cashier posting a payment between
the count and the dump would produce a backup whose recorded count never existed in the archive, and
the restore would then report a difference that was an artefact of how the backup was taken rather
than anything that had gone wrong.

So the counts and the dump come from one exported snapshot:

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ READ ONLY;
SELECT pg_export_snapshot();      -- held open for the whole backup
SELECT count(*) …;                -- 14 tables, same moment
-- pg_dump --snapshot=<id>        -- in a separate process
COMMIT;                           -- only after the dump has finished
```

An exported snapshot is valid only while its exporting transaction is open, which is why the
snapshot client is released in a `finally` block. Holding one connection for the length of a dump is
the cost of the guarantee.

`tests/integration/backups.test.ts` proves this rather than asserting it: it holds `pg_dump` open,
posts a payment while the snapshot is still held, then restores the archive into a **separate**
database and counts it directly. The recorded counts and the archive agree, and the subscriber
created mid-backup is correctly absent from both.

### Passwords never appear in the process list

`pg_dump` and `pg_restore` are spawned with no connection arguments. The host, port, user and
password go in `PGHOST`, `PGPORT`, `PGUSER` and `PGPASSWORD`; only the database *name* is passed as
`--dbname`, because `pg_restore` refuses to run without an explicit target even when `PGDATABASE` is
set, and a database name is not a secret.

On a shared office machine another logged-in user can read the process list, and a crash report can
quote arguments, so this is not a stylistic choice.

### Where the connection string comes from

From the pool, not from `process.env`:

```ts
connectionString: poolConnectionString(pool)
```

A backup taken from one database and restored into another is the one mistake this feature exists to
prevent, and two places configured separately is how that mistake gets made. If the pool was not
built from a URL, the service refuses rather than guessing.

### What a FULL backup does about attachments

For each file in the proof directory whose name matches the pattern the payment reader accepts and
which `payment_proofs` actually refers to:

- the SHA-256 is recomputed and compared with the digest stored at upload;
- a mismatch **abandons the backup** with `A stored payment proof no longer matches its recorded
  digest, so the backup was abandoned.` and the partial attachment folder is removed.

A backup carrying a corrupt attachment and claiming to be complete is more dangerous than one that
says what is wrong. A file with no `payment_proofs` row is left out rather than carried as an
unexplained extra.

The proof list is read inside the same snapshot, so the proofs carried are the ones the archive
refers to.

### What a restore does, in order

1. `backup.restore` permission.
2. `confirm: "RESTORE"` and a reason of at least three characters.
3. The record must be `COMPLETED`.
4. **Digest first.** If the file no longer matches its recorded SHA-256, the restore is refused with
   `DIGEST_MISMATCH` before anything is written. Overwriting a good database with a damaged file is
   the outcome a restore must never produce.
5. The archive is listed. An unreadable archive is refused with `UNREADABLE_BACKUP`.
6. Sessions holding an open transaction are ended:

   ```sql
   SELECT pg_terminate_backend(pid) FROM pg_stat_activity
   WHERE datname = current_database() AND pid <> pg_backend_pid() AND xact_start IS NOT NULL
   ```

   Only sessions that could actually block the restore. Killing every other session would also fail
   the requests of the other two office clients, which is not the API's business during a restore.
7. `pg_restore --clean --if-exists --single-transaction`. A partial restore rolls back, so the
   database is either restored or unchanged.
8. Migrations are applied, so a backup taken before a migration is not left on an old schema.
9. The fourteen counted tables are compared one at a time.
10. The row is set back to `COMPLETED` with `restored_at`/`restored_by`, and `backup.restore` is
    audited with the reason, the comparison result and every difference.

### Step 10, and the row inside its own archive

The archive contains this backup's own `backup_history` row as it stood mid-flight, because the row
is written before the dump. Restoring therefore rewinds that record to "Backup in progress".

It is put back to `COMPLETED` after the restore, and the reason is that this is exactly what
`COMPLETED` asserts: the file was read back and its counts checked. Left alone, the newest row in the
history would say the most recent backup failed.

### What the restore reports

```json
{
  "fileName": "…dump",
  "verified": true,
  "digestMatched": true,
  "rowCountsMatched": true,
  "differences": [],
  "attachmentsRestored": 1,
  "restoredAt": "…"
}
```

`differences` names each table with what the backup recorded and what is there now. A restore that
reported plain success while the subscriber count had changed would be worse than one that reports a
problem, so the detail travels with the verdict and the desktop shows the table.

## 2. Permissions

Backup permissions are split by what they do, not by which screen shows them:

| Permission | OWNER | ADMIN | AUDITOR | Others |
|---|---|---|---|---|
| `backup.view` | yes | yes | yes | no |
| `backup.verify` | yes | yes | yes | no |
| `backup.create` | yes | yes | no | no |
| `backup.restore` | yes | **no** | no | no |

`backup.view` and `backup.verify` are read-only: confirming that a backup still restores is an audit
function and must not require the ability to destroy the database. `backup.restore` is absent from
ADMIN and AUDITOR even though both may take and inspect backups, because it replaces every posted
figure in the system.

## 3. The desktop boundary

No backup operation returns bytes and none accepts a path.

| Bridge method | What crosses |
|---|---|
| `listBackups()` | The server's account of the history, plus the storage directory as text |
| `createBackup({ kind, note })` | A kind and a note |
| `verifyBackup(id)` | What the server found when it re-read the file |
| `restoreBackup(id, { confirm, reason })` | The confirmation word and the reason |

`BackupsPage.tsx` displays the storage directory so an operator knows where to copy a backup to
removable media, and never passes it back into another call.
`tests/unit/renderer-security.test.ts` asserts that no backup call takes a path, folder or file name,
and that no archive bytes cross the bridge.

The archive itself is only ever touched by the API's own `pg_dump` and `pg_restore` processes.

### Defects found and fixed while building this

- **`pg_restore` failed on every restore attempt.** `one of -d/--dbname and -f/--file must be
  specified`: unlike `pg_dump` and `psql`, `pg_restore` does not fall back to `PGDATABASE`. Fixed by
  passing the database name as `--dbname` while keeping the password in the environment.
- **A failed backup could not be read back at all.** `backup_byte_size CHECK (byte_size >= 1)` with a
  placeholder of `1` meant a recorded failure claimed a size it never had, and listing the history
  returned a 500. The constraint is now `>= 0` and a failed backup claims no size.
- **An unreadable failed record broke the whole history.** `z.record(z.enum([...]), …)` in Zod 4 is
  exhaustive, so the empty `row_counts` of a recorded failure failed validation and every listing
  returned 500. Changed to `z.partialRecord`.
- **A backup could describe a different database than the one being served.** The routes read
  `process.env.DATABASE_URL` while authentication used the injected pool. Now taken from the pool.
- **The row counts could not match the archive.** Counting in a separate transaction meant a payment
  posted during a dump was counted but not archived. Fixed with `pg_export_snapshot`.
- **Restoring killed every session on the database,** including the idle connections belonging to the
  other two office clients, which surfaced as `Connection terminated unexpectedly` in the pool. Now
  only sessions holding an open transaction are ended.
- **Restoring rewound the backup's own record to "Backup in progress".** Fixed by restoring it to
  `COMPLETED` after the counts have been checked.

### Limits

- A `FULL` restore puts back the proofs this backup carried and leaves any file added after the
  backup in place. Those files are unreferenced by the restored database, so they are harmless, but
  the proof directory is not returned to a byte-identical state.
- `BackupListSchema` exposes the storage directory so an operator can copy backups to removable
  media. The desktop displays it and never passes it back.
- `pg_dump` and `pg_restore` are taken from `PATH`. A deployment where they are not on `PATH` will
  record a failed backup with `spawn pg_dump ENOENT` rather than taking one.
- The screenshots above have not been reviewed by a human.

## 5. Security review, structured logs, indexes and data volume

### What was reviewed

The API surface, the logger, the Electron boundary and the PostgreSQL queries that carry the
office's money. The review is written down here because its findings are the evidence for the
task, not a claim about it: two real defects came out of it (below), and the rest is behaviour
that is now asserted by tests.

### Structured logging

`source/api/logging.ts` builds the logger options, and `source/api/app.ts` passes them to
Fastify. The defaults matter as much as the code:

| Setting | Value | Why |
|---|---|---|
| Level | `info` | A payment that fails to be written down is worse than a noisy log |
| `base.service` | `bcis-api` | Three office clients write to one file; the rows have to be separable |
| `timestamp` | ISO 8601, injected as `time` | A pasted log line has to be readable without a decoder |
| Key names | Pino's defaults (`level`, `time`, `msg`, `err`) | So a `jq` example in a runbook works against an unmodified tool |
| `redact` | 28 paths: headers (`authorization`, `cookie`, `set-cookie`, `proxy-authorization`), passwords, tokens and hashes, `DATABASE_URL`, `connectionString`, proof `base64` | A token is only ever a token; it is never logged in the first place |

Three details are worth stating because they are the ones that usually leak:

1. **Requests are serialized by hand.** `serializers.req` returns only the method, URL, request
   id, remote address and user agent. The default Pino serializer copies the whole header bag,
   which is where an `Authorization` header ends up in a log file that nobody reads carefully.
2. **Errors are scrubbed, not just redacted.** Redaction works on known field names, but a
   PostgreSQL error message can *contain* the connection string. `scrubSecrets` runs over the
   message and the stack of every logged error, so `password authentication failed for user
   "bcis_app"` and a `postgres://user:password@host/db` in a stack frame are both replaced
   before they are written. This was not theoretical: it was found by
   `tests/integration/security.test.ts`, which failed on the first run because the pool's
   `DATABASE_URL` was reaching the log through `err.stack`.
3. **The log stream is injectable.** `loggerOptions({ stream })` writes to any sink, which is how
   the tests read the real lines instead of a mock. The tests do not assert on a formatter.

Security events are named and stable, so a log query is a review rather than a guess:
`auth.login.succeeded`, `auth.login.failed`, `auth.session.revoked`, `security.unauthenticated`,
`security.permission_denied`. Every response carries `X-Content-Type-Options: nosniff`,
`X-Frame-Options: DENY` and `Referrer-Policy: no-referrer`; the API returns JSON only and is never
framed.

Test suites build the app with `logLevel: 'silent'` unless they are about logging. The logger is
still configured — it is simply not written anywhere — so a suite that is silent never has to
reopen a file handle to prove it wrote nothing.

### Indexes added (migration `0019`)

| Index | Query it serves |
|---|---|
| `invoices_open_service_idx` (partial) | "What does this service account still owe?" on the payment panel and the collections route |
| `invoices_open_subscriber_idx` (partial) | The same question by subscriber, for the receivable list and the dashboard |
| `payments_posted_subscriber_idx` (partial, `INCLUDE (amount_centavos)`) | "When did this account last pay, and how much?" on the statement |
| `audit_logs_created_idx` | The audit trail report, which reads a date range in order |
| `subscribers_*_trgm_idx`, `service_accounts_*_trgm_idx` (GIN, `gin_trgm_ops`) | `ILIKE '%term%'` search on the two tables that grow with the subscriber count |

The open-invoice indexes are partial on `balance_centavos > 0`, so a settled account costs
nothing and the index stays small on a database with years of closed invoices behind it.
`invoices_subscriber_idx` cannot serve the same query: its leading column is right, but the
open/closed filter is not in the index, so the closed rows are read too.

`pg_trgm` is a contributed extension. The migration installs it only if it is *available*, and
creates the trigram indexes only if it is installed, so a deployment on a restricted server
records no failed migration — search still works there, by scanning, and is simply slower on a
large list.

### The data-volume check

`scripts/performance-check.ts`, run with `npm run test:performance`. It builds a throwaway
database with 20,000 subscribers (6 billing months each), then measures the screens a collector, a
cashier and the owner actually use. Nothing is mocked: every measurement goes through the same
Fastify routes, services, SQL and Zod contracts the desktop calls. Reads are repeated and the
median is kept; writes are measured once, because repeating them would change the data rather
than the measurement. Environment variables: `BCIS_VOLUME`, `BCIS_MONTHS`, `BCIS_RUNS`,
`BCIS_KEEP=1` (keeps the database for inspection).

19 screens, 19 within budget. Seeded: 20,000 subscribers, 20,000 service accounts, 140,000
invoices, 140,000 invoice lines, 41,692 payments, 41,692 allocations, 181,692 ledger entries.

The harness does not stop at a time. It also asserts that the plans PostgreSQL chose are index
plans (`EXPLAIN ANALYZE`, requiring `subscribers_name_trgm_idx`, `invoices_open_service_idx` and
`payments_posted_subscriber_idx` by name and no sequential scan), and that the receivable total
still equals the stored open balances and the aging buckets still add back to it. A fast wrong
answer is worse than a slow right one.

Two things about the plan check are deliberate. It runs after `VACUUM (ANALYZE)`, because a bulk
insert leaves every heap page unvisited and every trigram index holding an unread pending list,
and PostgreSQL charges for both — the measurement would otherwise report a plan the office never
sees. And below the reviewed volume it checks that the index is *available* rather than *chosen*:
on a few thousand rows a scan is genuinely cheaper and the planner is right to pick it.

### Defects found and fixed by the volume check

- **`GET /receivables/summary` returned 500 at 20,000 subscribers.** `coalesce(sum(...),0)::int`
  is a 32-bit cast of a 64-bit sum, and the receivable across 20,000 accounts passes PHP
  21,474,836.47 without any single figure looking unusual. Every money aggregate that spans the
  whole office is now cast to `bigint` (receivables totals and aging, the dashboard, the revenue,
  aging, collections and billing-versus-collection reports, the collector and area roll-ups), and
  `readWideNumbersAsNumbers()` in `source/api/database.ts` converts 64-bit results to numbers once
  at the pool, so the published contracts are unchanged.
- **The plan check passed a scan that the office would never see.** Found while making the check
  itself trustworthy; the fix is the `VACUUM (ANALYZE)` above.

### Limits found by the volume check

- **A single billing cycle is capped at PHP 9,999,999.99.** `moneyBounds` in
  `database/schema.ts` constrains every *stored* money column to 999,999,999 centavos, and
  `billing_runs.total_centavos` is one of them. At PHP 999 per month that is about 10,000
  subscribers per cycle: a larger cycle fails the constraint with a clear error rather than
  silently truncating. This is the project's money ceiling, not a performance limit, and raising
  it is a decision about contracts and constraints rather than about speed. The read paths above
  are unaffected: a total that *summarises* many capped rows is not itself capped, which is why
  they are `bigint`.
- The volume check does not run the billing generation itself (it writes invoices directly, so
  the read paths are measured rather than the write path). Billing generation over 20,000
  accounts is bounded by the cycle ceiling above and by the per-account invoice count, not by
  anything measured here.
- **`npm audit` reports 8 high severity vulnerabilities**, all in the `electron-builder` chain
  (`app-builder-lib` → `@electron/get` → `got` → `http-cache-semantics`,
  [GHSA-ch52-4w7c-c8xp](https://github.com/advisories/GHSA-ch52-4w7c-c8xp)). The audit offers no
  fix except a breaking change. These are build-time dependencies of the installer and are not
  loaded by the running application or the API; the finding is carried into the installer item.
  The earlier recorded baseline of zero vulnerabilities predates the installer dependency.
- The evidence is machine-generated. No human has reviewed the timings against a real office
  network, a real disk and three clients at once.
